## Requirements

- **DIVE-IAM-REQ-029:** Dashboard HTTP paths MUST NOT include `/tenants/:tenantId` or another tenant-identifier segment. Product routes MUST NOT take tenant context from query string or body. `:centerId` and `:membershipId` remain resource selectors and never select the tenant.

- **DIVE-IAM-REQ-030:** After Clerk authentication, dashboard tenant context is an opaque server-stored handle presented in `X-Tenant-Context`, bound to the authenticated identity and Clerk `sid`. The handle selects a tenant and is not sufficient authorization. Roles, permissions, center scopes, and membership state are read from PostgreSQL on the request.

- **DIVE-IAM-REQ-031:** The server lists only the identity’s active operator memberships as opaque `operatorRef` values. Zero active memberships issue no handle. Exactly one active membership may be selected automatically. Several require an explicit `operatorRef` from that list on `POST /v1/me/tenant-contexts`. Invalid, inactive, unrelated, or cross-identity selections fail without disclosure. Several handles may exist for one Clerk session. The handle is tenant-scoped, not center-scoped.

- **DIVE-IAM-REQ-032:** A center application may issue the same tenant-scoped handle without `operatorRef` through `POST /v1/me/center-entry-contexts`. Its canonical MVP URL is `https://<centerKey>.app.<domain>` and its JSON body is `{ "centerRef": "<centerKey>" }`; `centerRef` and `centerKey` MUST carry the same value and are one untrusted selector expressed at the API and DNS boundaries, not two identifiers. The server derives `centerKey` from the exact request `Origin`, requires equality with `centerRef`, resolves trusted configuration to tenant + center, authenticates Clerk, and validates active membership, the stable `center.read` permission, and current center scope. Unknown, malformed, mismatched, inactive, cross-tenant, or unauthorized selection fails without disclosure. Success returns the tenant-scoped handle and internal `centerId`; subsequent product paths use `centerId`, not `centerRef`. The endpoint MUST NOT list other operators or centers. Center-application catalog and availability operations remain limited to that center even when the identity has other authorized centers. A trusted mapping has `active` or `disabled` state; only active mappings authorize CORS and center bootstrap. Tenant Owner and Tenant Admin may change that state with `center_entry.manage` through `PATCH /v1/centers/:centerId/entry-status`, with a non-empty purpose and tenant-scoped audit. Repeating the current state succeeds idempotently with `changed: false`. Disabling affects new CORS authorization and bootstrap only; it does not revoke tenant-scoped handles or define center-wide shutdown. Disabled mappings remain reserved tombstones and their `centerKey` cannot be deleted, renamed, reassigned, or reused in the environment. Custom center domains are outside the MVP.

## Authorization capability and application scope

**Documented -- Authorization capability:** [IAM](SPEC-DIVE-IAM-001.md), `DIVE-IAM-REQ-030..031` and [ADR-DIVE-008](../architecture/adrs/ADR-DIVE-008.md) own identity, active membership, roles, permissions and authorized center scopes. An identity can have permission over several centers of an organization. The handle selects the tenant, remains tenant-scoped, and is neither a grant of access nor an exclusive-center credential. Every request still checks its applicable authorization and resource boundaries.

**Documented -- Application scope, clarifying `DIVE-IAM-REQ-032`:** source: product-owner confirmation on 2026-09-30 of exclusive center-application scope, including when the same identity is authorized for other centers of the organization. This establishes transversal enforcement as a current product restriction, not a future proposal. It applies to every operation on center-owned data made through the MVP center application, not only catalog and availability. Application scope is an additional restriction on what that surface can expose or modify; it does not expand the identity's authorization capability.

- The center application MUST limit reads and writes to its trusted resolved center, even for an identity authorized for other centers in the same organization. The UI MUST NOT offer another center's data or a multi-center view from that application.
- The backend MUST enforce that restriction for details, lists, searches, aggregates and mutations, including resources whose center is resolved indirectly. Filtering or hiding data only in the UI is insufficient. Other centers' records, identifiers and aggregate contributions MUST NOT be returned through the center application.
- `GET /v1/centers` MUST NOT enumerate other centers when used by the center application; `GET /v1/centers/:centerId` and other resource operations MUST NOT use broader membership permissions to bypass application scope. A resource selector is not evidence of its trusted tenant or center ownership. Denials remain non-disclosing.
- Authentication, session lifecycle and genuinely organization-global operations retain their own approved contracts; this is not a blanket center filter for every HTTP request. An operation returning center-owned data is not organization-global merely because the caller is an administrator.
- The API MUST retain the per-request permission, membership, tenant-isolation and resource checks as well as the application-scope check. Neither dimension substitutes for the other. The policy belongs at a shared application/API authorization boundary, with resource ownership resolved by the owning feature, rather than being duplicated as catalog-specific rules or placed only in presentation code.

**Documented -- Future developments:** source: product-owner confirmation on 2026-09-30 of future permission-checked multi-center administration, while preserving authorization capability and application scope in future development. Existing and new center-facing features MUST preserve both dimensions. The tenant and handle boundaries remain as defined by `DIVE-IAM-REQ-030..031` and [ADR-DIVE-017](../architecture/adrs/ADR-DIVE-017.md). A future administrative application may define an explicitly approved multi-center scope within the tenant and the caller's current permissions. This preserves architectural capability, not an enabled MVP feature: it does not turn centers into tenants, narrow the tenant handle permanently to one center, or activate an aggregate administration surface in the MVP. New application scopes or exceptions require their own approved contract; a broad role alone does not select such a scope.

**Derived, Draft -- Verification obligation:** from the confirmed policy above, [IAM](SPEC-DIVE-IAM-001.md) `DIVE-IAM-REQ-028` and the [existing test/evidence workflow](../../docs/sdd/how-we-work.md#proportional-documentation-and-evidence), verifying authorization capability does not by itself verify application scope. Changes to center-facing features should identify their checks for each dimension separately and supply executable proof for the affected public boundaries. This reporting form remains a derived Draft proposal rather than an explicitly confirmed product instruction. Existing catalog checks are not proof that all center-facing endpoints implement the current application-scope restriction.

### Illustrative example

**Derived, Draft:** an administrator has current permission over Puerto and Bahia in the same organization. From Puerto's application, only Puerto's permitted data is accessible; a center list, direct Bahia resource request or aggregate MUST NOT expose Bahia's data. Navigating to Bahia's own application allows access there only after its own entry and current authorization checks. The identity's multi-center capability and the tenant-scoped handle model remain intact. A future, separately approved administrative surface could consult both centers; no such surface is enabled by this decision.

### Trusted resolution and enforcement

**Proposed, Draft:** establish a server-resolved application scope at a shared API/application authorization boundary, before executing a center-data operation. This is an additional restriction, not a replacement for the existing tenant context or per-request authorization. The conceptual scope identifies the selected tenant and center and the verified source of the application association; these are not new client-authoritative fields or a selected wire format.

| Boundary | Proposed, Draft contract |
|---|---|
| Identity | Verify the Clerk standard session JWT under the [IAM validity boundary](SPEC-DIVE-IAM-001.md#dashboard-jwt-validity-boundary) before trusting claims used to establish application scope; do not require session/user-status lookup. Never derive authority from an unverified token payload. |
| Center association | Resolve the exact canonical center origin through the existing environment host policy and trusted center registry. A hostname match alone is insufficient; manual per-center allowlists and wildcard acceptance are not the proposed runtime allocation mechanism. |
| Tenant agreement | Require agreement between the resolved center's tenant, the authenticated identity's authorized tenant context and the operation's resource ownership. A supplied resource ID cannot select another scope. |
| Resource operations | Compare the requested or indirectly resolved resource center with the trusted application scope before reads or side effects. For lists, searches and aggregates, constrain the data query itself to that scope rather than filtering only the UI or a completed response. |
| Missing scope | Deny center-data operations when no valid application scope can be established. Missing or forged `Origin`, a configured general origin, or an Owner/Admin role cannot select a multi-center scope. Genuinely global operations retain their own contracts. |
| Failures | Resolver errors grant no scope and cause no operation side effects. Keep invalid-scope denials non-disclosing and distinguish operational unavailability without disclosing another center. No authorization cache is proposed. |

### Approved service admission and bootstrap

**Documented -- Approval and boundaries:** source: product-owner approval on 2026-09-30 of the recommended conventional simple BFF closure following the documentation review. The selected mechanism is HTTPS with a server-only service credential, separate user authentication, a BFF host-resolved center association, bootstrap without a pre-existing tenant handle, and the global-admission/exception controls below. This approval selects the mechanism and ordering, not unexecuted deployment evidence, a new session lifecycle, a new public/widget authorization scheme or a particular secret/header name.

| Stage | Documented approved behavior |
|---|---|
| Service credential | Provision the credential only to the permitted BFF and API through server-side deployment secrets, separated by environment. Carry it independently of the Clerk bearer; do not place it in browser-visible configuration, cookies, URLs, responses or logs. Document and validate provisioning, rotation and immediate compromise revocation in the deployment configuration. No additional JWT, per-request signature, nonce persistence or credential TTL is selected. Missing or invalid service authentication grants no BFF authority. |
| Center association | The BFF validates its canonical request host against environment configuration and trusted mappings, discards client-supplied service/scope metadata and builds the upstream association itself. The API authenticates the BFF before accepting that association, re-resolves mapping ownership and verifies the current user/resource boundaries. A body/path center selector cannot replace the host-derived association. Neither side claims to prove the user's physical browser location. |
| First center bootstrap | The browser sends the Clerk bearer, required exact browser Origin and existing `{ centerRef }` body to the same-origin BFF; no `X-Tenant-Context` exists yet. The BFF checks host/Origin/selector agreement and forwards the validated original Origin, user token and body with its service credential and association to `POST /v1/me/center-entry-contexts`. The API requires BFF and current Clerk authentication but no pre-existing tenant handle for this classified operation; it preserves [ADR-DIVE-017](../architecture/adrs/ADR-DIVE-017.md#center-application-entry) active-entry, exact-Origin, membership, `center.read` and scope checks before issuing the existing tenant handle. Do not synthesize Origin for a browser request that omitted it or make bootstrap an anonymous/public exception. |
| Subsequent center-data calls | The browser sends Clerk bearer and issued `X-Tenant-Context` to the BFF; the BFF adds only server-owned service authentication and center association. API admission authenticates the service and user, resolves the session-bound tenant handle, checks tenant/center agreement and applies current permission and direct/indirect resource ownership. Lists and aggregates constrain the query to the resolved center. |
| Other classified operations | Preserve each existing identity, operator/tenant-context, public/channel/capability, webhook and infrastructure contract. Classify them explicitly and back any non-center exception with its owner; do not apply the first-center-bootstrap handle exception to arbitrary routes. No native/script or multi-center administrative access is introduced. |

### Approved BFF protocol and browser boundary

**Documented -- Decision record and exact source:** the product owner explicitly approved the preceding BFF protocol, credential, ingress, error-separation and verification recommendation in this implementation-planning chat on 2026-09-30, then requested that the approved decisions be recorded in their normative owner. That approval selects the decisions below; the separate request to propose an exception inventory does not approve its classifications. This record paraphrases the decision rather than reproducing the chat. Existing authority remains in `DIVE-IAM-REQ-030..032`, [service admission/bootstrap](#approved-service-admission-and-bootstrap), [ADR-DIVE-008](../architecture/adrs/ADR-DIVE-008.md) and [ADR-DIVE-017](../architecture/adrs/ADR-DIVE-017.md).

| Boundary | Documented decision approved 2026-09-30 |
|---|---|
| Service transport | Use `X-BFF-Service-Credential: <version>.<secret>` independently of `Authorization: Bearer <Clerk token>`. The secret is 32 cryptographically random bytes encoded in base64url. Only the BFF holds the raw secret; the API holds its SHA-256 verifier and non-secret version and compares hashes in constant time. Configuration is explicit and required, without fallback credentials. |
| Application association | Use `X-BFF-Center-Origin` for the canonical center origin resolved and validated by BFF server code. Discard browser-supplied service/scope metadata. The API authenticates the service before accepting the association, re-resolves trusted mapping ownership and checks tenant/resource agreement. No browser-supplied tenant or center becomes authority. |
| Ingress and upstream | Require HTTPS, a fixed configured API upstream and no following of upstream redirects that could forward credentials. ### Approved service credential operations

**Documented -- Source and scope:** the initial product-owner documentation request on 2026-09-30 retained this procedure as a proposal. The subsequent explicit [protocol/operations approval](#approved-bff-protocol-and-browser-boundary) selects its provisioning, planned-rotation and compromise-revocation procedure. This closes procedural approval, not the hosting provider configuration, operational assignment or proof of effective revocation. The original anchor above remains available for existing references; the previously proposed procedure is no longer pending approval.

| Operation | Documented approved procedure |
|---|---|
| Credential allocation | Allocate a cryptographically random secret with a non-secret version identifier to the logical BFF in each environment, not to individual centers. Replicas remain instances of that BFF, not additional application authorities. Keep development, test and production secrets independent; previews receive no production credential. During rotation, old and new versions may coexist only for the transition below. |
| Provisioning | Use the 32-byte/base64url secret, SHA-256 verifier and `X-BFF-Service-Credential` transport selected in the [approved protocol](#approved-bff-protocol-and-browser-boundary). Store the raw secret in the BFF's server-side deployment secret scope and only its expected verifier and version in API protected configuration. Access is limited to authorized deployment/service roles; the API verifies presented credentials before accepting scope. Do not put the secret in Git, browser bundles, `NEXT_PUBLIC_*`, cookies, URLs, responses or logs. |
| Planned rotation | Generate a new version; update every API instance to accept the current and new verifiers; then deploy the BFF with the new secret. Verify that all BFF instances use the new version and exercise both bootstrap and a subsequent protected operation. Remove the old verifier from every API instance and verify old-key rejection. End the overlap when the transition completes rather than introducing a session TTL. Record progress by version/deployment identifiers, never secret values. |
| Rollback | During the planned overlap, rollback may use the still-accepted version. After retirement or compromise, rollback must not restore its verifier or secret. Include old revisions, rolling replicas, autoscaling sources and reachable deployment aliases in the configuration/traffic inventory; restoring an old application build must not restore retired authentication authority. |
| Compromise revocation | Withdraw the compromised verifier from API admission first, without a grace overlap. Revocation is effective only when no reachable API instance accepts it. If that cannot yet be guaranteed, suspend affected BFF-dependent traffic at trusted admission/ingress while removing stale instances; never fall back to direct unscoped API calls. Provision a replacement and resume only after verifying old-key rejection and valid replacement behavior. Investigate exposure and access; separate Clerk-session or tenant-handle invalidation depends on incident scope, not automatic service-key rotation. This suspension does not modify center-entry mapping states or introduce a center shutdown lifecycle. |
| Environment-secret limitation | An environment-variable update alone does not replace values already loaded by running instances. Inventory and retire/reconfigure every stale instance before declaring revocation complete. The initial recommendation uses deployment secrets with controlled instance replacement; it does not prove immediate withdrawal. If immediate revocation without redeployment is required, an execution-time credential registry requires a separately selected and verified contract; no new registry, database table or cache lifetime is selected here. |
| Planned checks | Reject missing, invalid, retired and other-environment credentials; retain user/context checks with a valid service key. Exercise bootstrap and subsequent calls during rotation, verify rejection on every reachable API deployment after retirement, and test that rollback cannot restore revoked authority. Check that secrets are absent from browser assets, responses and logs. These are planned tests and deployment checks, not executed coverage. |

**Documented -- Remaining configuration and activation limits:** the procedure, transport and entropy/verifier choices are approved. Deployment secret provider configuration, the responsible operational role and any rotation cadence remain unresolved; no TTL or numeric cadence is selected. Verify instance inventory, ingress suspension and replacement behavior against the approved compromise-revocation obligation. Do not claim that asynchronous environment-secret propagation satisfies immediate revocation. If the chosen deployment cannot meet that obligation, resolve the gap before activation rather than silently weakening it or treating the alternative registry as approved.

### Avoiding route omissions

**Documented -- Approved controls:** the product-owner decision on 2026-09-30 to prevent omissions adopts global admission, explicit exceptions and route-inventory checks. These are required implementation and review checks, not claims that the current application or CI already implements them.

| Control | Documented obligation |
|---|---|
| Global admission | Register admission through Nest `APP_GUARD`, not only optional controller/method `@UseGuards`. An unclassified operation is denied by default even with valid user and BFF credentials. Absence of metadata never means public or global. |
| Explicit classification | Classify every runtime operation by owner and data authority. Center-data routes require BFF and resolved center scope. Identity/bootstrap, genuinely global operations, public channel/capability endpoints, provider webhooks and infrastructure retain explicit, distinct owning contracts. A URL prefix, missing Origin, broad role or client flag cannot select an exception. |
| Exception inventory | Maintain one code-owned inventory of approved non-center admission exceptions, with method/path, owning SPEC/ADR IDs and admission mechanism. Automatic route discovery checks metadata against that inventory; a generic public decorator or controller override cannot exempt an unlisted route. New exceptions require contract review, not just making an inventory test pass. |
| Resource enforcement | Route admission does not establish resource ownership. Each use case resolves direct/indirect ownership and constrains its queries/effects using the trusted scope. A route classified as global must not return center-owned data under that classification. |
| Non-controller surfaces | Business-data HTTP handlers outside Nest controllers are disallowed unless they pass the same shared admission and scope boundary. Include raw middleware, custom adapters and other registered handlers in the surface review; a Nest controller inventory alone is insufficient. |
| Executable gate | Add an automatically discovered route-classification/exception test to the existing API validation path and CI test gate. Fail when a route is unclassified, classification conflicts, an exception lacks authority, or admission wiring is missing. Test the real application composition, not only isolated guard mocks. |
| Negative behavior | Prove that a newly registered test controller with no classification is denied; direct API calls with valid Clerk/context but no valid BFF are denied; client scope/service-header tampering cannot change authority; and valid BFF scope for A cannot expose or mutate B even when the user is authorized for both. Include lists, aggregates, indirect ownership, revocation, resolver failure and mutation non-effects. |

**Documented -- Limits:** the same approved recommendation distinguishes omitted protection from intentional misclassification. Deny-by-default prevents an accidental omission from exposing a route; discovery cannot establish the business meaning of an operation. Reviewers must still check exception legitimacy and ownership/query enforcement. Neither passing catalog tests, CORS, agent instructions nor a route count proves universal conformance.
